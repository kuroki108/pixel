# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Pixel is a Discord bot (discord.py) for the "zen arcade" Discord server. It is a single-guild bot: most behavior is gated to one hardcoded guild via IDs in `config.py`, and text in embeds/messages is German.

## Running the bot

- Entry point: `python bot.py` (runs the `ZenArcadeBot` defined there).
- Requires `DISCORD_TOKEN` in the environment or a `.env` file (see `.env.example`); loaded via `python-dotenv` if installed, otherwise `.env` is silently skipped and the bot exits with an error at startup if no token is found.
- Install deps: `pip install -r requirements.txt`. Note: `discord` and `discord.py` (and `dotenv`/`python-dotenv`) are two different PyPI packages that both install into the same top-level module namespace — only `discord.py` and `python-dotenv` belong in `requirements.txt`; never add the other two back.
- There is no test suite, linter, or build step configured in this repo.
- `config.GUILD_ID` controls slash-command sync: if set, commands sync instantly to that guild only (`tree.copy_global_to` + `tree.sync(guild=...)`); commands only sync globally (slow, up to 1h propagation) if `GUILD_ID` is falsy.

## Architecture

`bot.py` is the single composition root for the whole bot — everything (including the leveling system) loads through it; there is no separate entry point anymore.
- Defines `ZenArcadeBot(commands.Bot)` and loads a fixed list of cogs as extensions (`INITIAL_EXTENSIONS`): `ticket_system.panels`, `onboarding`, `counting`, `log`, `number_guessing`, `birthday`, `media_threads`, `lvl_system.cogs.leveling`, `moderation.cog`, `moderation.voice`, `free_games.cogs.checker`, `free_games.cogs.tools`, `free_games.cogs.settings`, `tictactoe.cog`, `leaderboard`.
- `setup_hook` connects `self.db` (a `modules.database.Database`, SQLite via `aiosqlite` — the bot-wide **master DB**, see below) **before** extensions load, because `leveling.py`/`counting.py`/`birthday.py`/`number_guessing.py`'s `setup()` all read `bot.db`. It also binds the ticket system's `TicketStore` singleton to the same connection (`ticket_store.bind(self.db.conn)`) and triggers its one-time JSON migration, since the ticket store isn't a cog and has no `cog_load()` hook of its own. `close()` is overridden to close the connection on shutdown.
- Selfroles (`modules/selfroles.py`, `modules/self_cute_roles.py`) are **not** cogs/extensions — their persistent views are registered manually in `setup_hook`, and their posting commands (`!selfroles`, `!cute_role`) live directly in `bot.py` as prefix commands guarded by `@commands.has_any_role(*config.ADMIN_ROLES)`. Both commands load their image asset via `discord.File(ASSETS_DIR / "...")`, where `ASSETS_DIR` is resolved from `bot.py`'s own location — this makes them independent of the process's current working directory.
- All persistent (`timeout=None`) views must be re-registered via `bot.add_view(...)` in `setup_hook` on every restart, since discord.py doesn't restore them automatically. `modules/ticket_system/views.py::all_persistent_views()` centralizes this for the ticket system.
- `on_command_error` is the single global handler for **prefix** commands (`!selfroles`, `!set`, …) and catches `MissingAnyRole`/`MissingPermissions`/`MissingRole` with one friendly message. A cog-level `@command.error` handler (e.g. `counting.py`'s `set_number_error`) takes priority over this global one for that specific command when present — if you add a new prefix command with its own local error handler, make sure it checks the exception type `has_any_role`/`has_permissions` actually raises (`MissingAnyRole` vs `MissingPermissions` are not interchangeable).

`config.py` is the **master config**: every Discord snowflake ID used operationally anywhere in the bot (channels, categories, admin/staff roles) lives here, grouped by feature in comment sections, and every module that needs one does `from config import THE_CONSTANT` (aliased with `as` where the module's local name differs) rather than hardcoding it locally. `config.ADMIN_ROLES` (tuple, prefix commands) also replaced the old `bot.py`-local constant, which `counting.py` used to import back from `bot` (`from bot import ADMIN_ROLES`) — a fragile pattern that only worked because extensions loaded after `bot.py` had fully executed; now everything imports `ADMIN_ROLES` from `config` directly and that ordering dependency is gone. Deliberately **excluded**: the dozens of granular self-assign role IDs inline in `modules/selfroles.py`/`modules/self_cute_roles.py`'s `discord.SelectOption(value=...)` catalogs — those are UI content next to their own usage, not "which channel/who's staff" operational config, and moving them here would only bloat the file. `SUPPORT_CATEGORY_ID == APPLICATION_CATEGORY_ID` and `SUPPORT_STAFF_ROLE_ID == APPLICATION_STAFF_ROLE_ID` intentionally point at the same IDs (single support-staff role/category serving both ticket kinds) — left as-is. No env-based overrides except the bot token.

### Master database (`modules/database.py`)

One `aiosqlite` connection (WAL mode), one file (`data/pixel.sqlite3`), owned by `ZenArcadeBot.db` and created in `setup_hook` before any extension loads. Grew out of the old leveling-only DB (`modules/lvl_system/database.py`, now deleted) — every feature needing persistence gets a table here instead of its own JSON file. Sections: `users`/`level_roles`/`guild_config` (leveling), `counting_state`, `number_guessing_scores`, `birthdays`, `birthday_calendar_messages`, `mod_cases` (moderation), `free_games_guild_settings`/`free_games_posted_deals`/`free_games_state` (free games), `ttt_stats` (tic-tac-toe), `leaderboard_messages` (combined, paged leaderboard), `tickets`/`ticket_counters` (schema only — the ticket system owns its own query layer, see below). Each cog gets the shared instance via `bot.db` in its `setup(bot)` function (established first by `leveling.py`, now followed by `counting.py`/`birthday.py`/`number_guessing.py`/`moderation/cog.py`/`free_games/cogs/*.py`/`tictactoe/cog.py`/`leaderboard.py`) and stores it as `self.db`.

**Migration on first start (one-time, automatic, non-destructive):** `Database.connect()` first copies (never moves) the old `modules/lvl_system/data/leveling.sqlite3` to the new master DB path if the new file doesn't exist yet, then imports any legacy JSON file into its matching table — but only if that table is still empty, so restarts are idempotent and re-runs are safe. After a successful import the JSON file is renamed to `<name>.json.migrated` (never deleted), so a failed or partial migration always leaves the original data recoverable on disk. `Database._migrate_free_games_db()` and `Database._migrate_tictactoe_db()` follow the same idempotent pattern for a legacy *SQLite* file instead of JSON: if `data/legacy_free_games.sqlite3` / `data/legacy_tictactoe.sqlite3` exists and its target table is still empty, rows are imported via a second `aiosqlite` connection, then the file is renamed to `.sqlite3.migrated` (never deleted). Ticket migration (`tickets.json` → `tickets`/`ticket_counters`) is handled separately by `TicketStore.migrate_legacy_json()` (called explicitly from `setup_hook`, since `TicketStore` isn't a cog and has no automatic lifecycle hook) rather than from `Database` itself, keeping the ticket system's persistence details inside its own layer. If you add a new feature needing persistence: add a table to `SCHEMA` in `modules/database.py`, add its query methods there (or, for a self-contained subsystem like tickets, in that subsystem's own storage module bound to `db.conn`) — don't invent a new JSON file.

### Ticket system (`modules/ticket_system/`)

The most substantial subsystem. Layers:
- `panels.py` — slash commands (`/setup-support`, `/setup-bewerbung`) that post the entry-point panel embeds/views into a channel.
- `views.py` — all Discord UI: `SupportPanelView`, `ApplicationPanelView` (button → opens a ticket or an application modal), `TicketControlView` (Claim/Close/Transcript/Add/Remove/Delete buttons posted inside each ticket channel), plus short-lived ephemeral helper views for user add/remove and delete confirmation.
- `modals.py` — application forms (Supporter/Designer/Event Manager); `on_submit` calls into `ticket_manager.create_ticket` via a shared `_finish_application` helper.
- `ticket_manager.py` — all ticket business logic (create/close/claim/delete/add/remove user, transcript generation), used by both `views.py` and `modals.py` so the logic exists in one place. `create_ticket` reserves a ticket slot via `store.reserve_ticket_slot(...)`, which checks the per-user open-ticket limit and increments the channel-numbering counter atomically under one lock — don't split that check-then-increment back into two separate store calls, that reintroduces a race where rapid double-clicks can exceed `MAX_OPEN_*_TICKETS_PER_USER`.
- `permissions.py` — role/permission checks (`is_staff_for_ticket_type`, `is_admin`, etc.), all keyed off `config.py` role IDs.
- `storage.py` — persistence layer: `TicketData` dataclass + `TicketStore`, backed by the `tickets`/`ticket_counters` tables in the master SQLite DB (`modules/database.py`). `store = TicketStore()` is a module-level singleton created at import time, before the DB connection exists — `bot.py`'s `setup_hook` calls `store.bind(conn)` to hand it the shared `aiosqlite.Connection` (any store method called before `bind()` raises `RuntimeError` rather than failing silently), then `await store.migrate_legacy_json()` to one-time-import the old `data/tickets.json` (only if the `tickets` table is still empty; the file is renamed to `.json.migrated` afterward, never deleted). All queries go through one `asyncio.Lock()` per store instance — `reserve_ticket_slot` holds it across the open-ticket-count check *and* the counter increment so concurrent ticket creation can't race past `MAX_OPEN_*_TICKETS_PER_USER`. `added_users`/`answers` are stored as JSON-text columns (never queried independently of their ticket, so a join table would be pure overengineering here). Malformed legacy entries (missing `opener_id`/`type`/`channel_id`) are skipped during migration rather than raising `KeyError`.
- `transcript.py` — builds an HTML transcript of a channel's message history for the Transcript button / delete-log.

Ticket "type" strings (`"support"`, `"application_supporter"`, `"application_designer"`, `"application_eventmanager"`) drive category placement, staff-role resolution, and per-type open-ticket limits (`config.MAX_OPEN_SUPPORT_TICKETS_PER_USER` / `MAX_OPEN_APPLICATION_TICKETS_PER_USER`) — application sub-types share one combined limit/category via the `"application"` prefix check in `ticket_manager._category_and_prefix`/`create_ticket`.

### Leveling system (`modules/lvl_system/`)

Integrated as a regular cog (`lvl_system.cogs.leveling`), loaded through the main `ZenArcadeBot` — it is **not** a separate bot process. All internal imports already use the absolute `modules.lvl_system...` form, which is what makes this work when loaded from the repo root.
- Its DB tables (`users`, `level_roles`, `guild_config`) and query methods live in the bot-wide master `modules/database.py` now, not in a lvl_system-local file — see "Master database" above. `lvl_system/cogs/leveling.py` just imports `Database` from there like every other persistence-using cog.
- `cogs/leveling.py` — text-XP (`on_message`, cooldown-gated, skips channels in `config.NO_TEXT_XP_CHANNEL_IDS`), voice-XP (`tasks.loop` every 60s, skips solo voice channels, the guild's AFK channel, and channels in `config.NO_VOICE_XP_CHANNEL_IDS`; caps a user at `VOICE_XP_CAP_MINUTES` (90) per rolling 24h window via an **in-memory** `voice_xp_tracker` dict — resets on restart, see known weaknesses), automatic level-role assignment, and slash commands: `/rank`, `/xp add|remove|set|reset|reset-server` (admin), `/level-config show|text-xp|voice-xp|levelup-channel` (admin). Its own `/leaderboard` command was removed in favor of the combined one in `modules/leaderboard.py` — see below.
- `utils/leveling_math.py` — pure XP curve (`5*level² + 50*level + 100` XP per level).
- `utils/rank_card.py` — generates the `/rank` PNG via PIL; loads fonts from the repo-root `assets/fonts/DejaVuSans{,-Bold}.ttf` (shared with `onboarding.py`'s welcome image, moved there from the old per-module `assets_lvl/` copy) so a font is always available regardless of host OS.
- Requires the `voice_states` intent (set in `bot.py`) for the voice-XP loop's channel-member checks, and the `aiosqlite` package (in `requirements.txt`).
- `scripts/dedupe_commands.py` is a standalone maintenance script (not imported by the bot) for removing duplicate global/guild slash commands via the raw Discord API; run manually with `DISCORD_TOKEN` (and optionally `DEV_GUILD_ID`) set. It needs the `requests` package, which is intentionally **not** in `requirements.txt` since it's a dev-only tool, not a bot runtime dependency.

### Moderation system (`modules/moderation/`)

Merged in from a previously separate standalone bot ("modbot") — ported as two cogs sharing one small package instead of running as its own process/token. Layers:
- `cog.py` — the `Moderation` cog: `/ban`, `/kick`, `/timeout`, `/warn`, and a `user_group` (`/user info`). Each of the four moderation actions goes through `_log_case()`, which writes a row via `bot.db.add_mod_case(...)` (master DB, see below) and builds a case-numbered embed (`utils.build_case_embed`) that's both sent as the interaction response **and** posted to `config.MOD_LOG_CHANNEL_ID` via `utils.send_log`. `/user info` reads `bot.db.get_user_mod_case_counts`/`get_user_mod_cases` to show a stats summary + the 3 most recent cases for a member.
- `voice.py` — the `Voice` cog: a `vc_group` (`/vc move|disconnect|mute|unmute|muteall|unmuteall|moveall`). Stateless — no DB access, pure Discord API calls guarded per-command by native permissions (`move_members`/`mute_members`).
- `utils.py` — `build_case_embed`/`CASE_EMOJIS`/`CASE_LABELS` (embed rendering), `send_log` (posts to `config.MOD_LOG_CHANNEL_ID`), `check_hierarchy` (blocks self-moderation, moderating the owner, moderating someone with an equal/higher top role than the actor, or a target whose top role is above the bot's own — returns a German error string or `None`).

**Permission model differs from the rest of the bot on purpose (carried over from modbot):** every command here uses `@app_commands.checks.has_permissions(...)` against real Discord guild permissions (`ban_members`, `kick_members`, `moderate_members`, `move_members`, `mute_members`) rather than `config.ADMIN_ROLES`/`ADMIN_ROLE_ID` or a ticket-system-style role check. This was kept as-is rather than unified — see "Permissions are conceptually still split" below, now a four-way split instead of three.

**Case storage** lives in the master DB's `mod_cases` table (`modules/database.py`: `add_mod_case`/`get_user_mod_cases`/`get_user_mod_case_counts`), not a JSON file — unlike modbot's original `storage.py`, which tracked cases in `data/cases.json` (relative to the old modbot root) with a manually incremented `next_case_id`. That old file was **not** migrated into the master DB: its case rows belong to a different (test) guild ID than `config.GUILD_ID`, so they'd be permanently invisible to every guild-scoped query here anyway. The file itself was left on disk untouched (now at `modules/modbot/data/cases.json`, after the leftover `modbot/` folder was moved under `modules/`) rather than deleted, in case it's ever needed for reference; everything else from the old `modbot/` folder (`main.py`, `config.py`, `storage.py`, `utils.py`, `cogs/`) was removed earlier since its logic now lives in `modules/moderation/`.

**Dedup with `log.py`:** discord.py fires `on_member_ban`/`on_member_remove` regardless of *how* a ban/kick happened, so without special handling, `/ban` and `/kick` would produce two log messages in `MOD_LOG_CHANNEL_ID` — one generic audit-log-based embed from `log.py`, one case-numbered embed from here. `log.py`'s `on_member_ban`/kick-detection in `on_member_remove` now check whether the audit-log actor is the bot itself (`banned_by.id == guild.me.id` / `kicked_by.id == member.guild.me.id`) and `return` early if so, since `moderation/cog.py` already logged that action. `log.py` still logs bans/kicks performed outside the bot (e.g. directly via Discord's UI) — that catch-all behavior is preserved. `timeout`/`warn` have no Discord gateway event to dedup against (no prior `log.py` coverage existed for either), so they only ever log once, from here.

### Free Games (`modules/free_games/`)

Merged in from a previously separate standalone bot (its own `config.py`/`database.py`/`freestuff.db`, no `main.py`/entrypoint carried over — that runner file was lost before the merge, so `cogs/checker.py` below was rewritten from scratch against the surviving pieces rather than ported). Layers:
- `deal.py` — the `Deal` dataclass: a source-agnostic normalized offer (`deal_id`, prices in cents, `is_free`, optional `end_date`/`rating`). `deal_id` encodes the source and a natural end-date/appid so the same still-active offer always dedupes to the same ID (e.g. `"epic:{slug}:{endDate}"`, `"steam:{appid}:{expiration_ts}"`).
- `sources/epic.py` / `sources/steam.py` — each exposes `fetch_candidates(session) -> list[Deal]` (list scrape) and `enrich(session, deal) -> Deal` (per-deal detail fetch — Epic's list response already has everything so `enrich` is a no-op there; Steam's list response lacks description/rating, so `enrich` calls `appdetails` for those, and is therefore only invoked for deals that pass the not-already-posted filter in `checker.py`, not for every candidate).
- `embeds.py` — `build_embed`/`build_view`: green embed for `is_free` deals, orange for discount-only, plus a link-style "Im Browser öffnen" button (no `custom_id`, so it needs no `bot.add_view` registration).
- `cogs/checker.py` — the `FreeGamesChecker` cog, the actual automation: a `tasks.loop(minutes=config.FREEGAMES_CHECK_INTERVAL_MINUTES)` that queries both sources, skips deals already in `free_games_posted_deals` (via `bot.db.is_free_game_deal_posted`), applies the per-guild `only_free` setting (skips discount-only deals unless a server opted into `/settings modus` → "auch Rabatte"), enriches and posts new ones to `config.FREEGAMES_CHANNEL_ID` (pinging `config.FREEGAMES_PING_ROLE_ID` if set), then marks them posted. Owns one `aiohttp.ClientSession` for the cog's lifetime, opened in `cog_load`/closed in `cog_unload` (both async — discord.py awaits both, not just `cog_load`).
- `cogs/tools.py` — `/test` (posts a hardcoded example embed to preview styling) and `/status` (shows last-check time, interval, configured channel/role, current mode) — both native-`manage_guild`-gated like the rest of this module, not `config.ADMIN_ROLES`.
- `cogs/settings.py` — `/settings modus` (toggle `only_free` per guild) and `/settings anzeigen`.

Channel/ping-role/interval are fixed in `config.py` (`FREEGAMES_CHANNEL_ID`/`FREEGAMES_PING_ROLE_ID`/`FREEGAMES_CHECK_INTERVAL_MINUTES`), not `.env`-driven like the original standalone bot was — consistent with the rest of Pixel's "no env overrides except the token" rule. `only_free` is still a per-guild DB setting (`free_games_guild_settings`) even though Pixel is single-guild, matching the same not-worth-collapsing pattern already used for `guild_config`/`level_roles`.

### Other cogs

- `onboarding.py` — two cogs: `Onboarding` (auto-assigns `config.ONBOARDING_ROLE_IDS` on member join) and `WelcomeImageCog` (generates a PIL-composited welcome image from the member's avatar + `assets/background.png`; PIL work runs via `asyncio.to_thread` to avoid blocking the event loop; fonts come from the shared `assets/fonts/` DejaVu files, same as the rank card).
- `counting.py` — counting-game cog for one channel (`config.COUNTING_CHANNEL_ID`), with a hardcoded `ACHIEVEMENTS` dict of milestone numbers, plus `!set` admin override. Count + last-user state live in memory (`self.count`/`self.last_user_id`, mutated synchronously with no `await` in between so there's no read-then-write race across messages) and are persisted to the master DB's `counting_state` table after every change, loaded back in `cog_load()`.
- `log.py` — mod/audit logging cog, posts to three separate log channels (`config.MESSAGE_LOG_CHANNEL_ID`/`MEMBER_LOG_CHANNEL_ID`/`MOD_LOG_CHANNEL_ID`: message edits/deletes, member join/leave/kick, ban/unban) with 1s audit-log-lag delay before attributing kicks. Its ban/kick logging skips events the bot itself performed (i.e. via `/ban`/`/kick`) — see "Moderation system" above for why.
- `number_guessing.py` — `/number_guessing`. Only **one global game at a time** (`self.game: dict | None`, not per-user) — a second `/number_guessing` while one is active gets an ephemeral "already running" reply. Each game has a 2-minute timer (`asyncio.create_task` + `asyncio.sleep`, cancelled on a correct guess) that auto-ends the game and frees it up for the next player. A point is awarded only if guessed in ≤7 attempts **and** within the time limit, persisted via `db.add_number_guessing_point()`. The active game/timeout task itself is deliberately **not** persisted (ephemeral runtime state, not "storage"). Its own `/number_score` leaderboard command was removed in favor of `modules/leaderboard.py` — see below.
- `birthday.py` — `/birthday set|remove` (any member, no permission gate) and `/kalender`, styled like the leveling leaderboard used to be. Birthdays live in the master DB's `birthdays` table (`user_id` primary key — no more string/int key juggling now that it's not JSON). A daily `tasks.loop` (`REMINDER_TIME_UTC`, 08:00 UTC) posts a congratulation embed + mention into `config.BIRTHDAY_CHANNEL_ID` for anyone whose day/month matches today. `/kalender` embeds are **self-updating**: the posted message's `(channel_id, message_id)` is tracked in the `birthday_calendar_messages` table (one live message per channel — a repeat `/kalender` in the same channel just retargets tracking to the new message) and re-rendered via `message.edit(...)` whenever a birthday is set/removed, after the daily reminder run, and by a second daily loop (`CALENDAR_REFRESH_TIME_UTC`, 00:05 UTC) that exists purely to keep the "days until" ordering/🎂-marker correct even on days with no changes. Stale tracked messages (deleted message/channel) are dropped automatically instead of erroring.
- `leaderboard.py` — the merged replacement for the old per-feature `/leaderboard` (leveling) and `/number_score` (number-guessing) commands: one `/leaderboard` command, one category per page (Level → Tic-Tac-Toe → Number-Guessing), paged via a `◀ N/3 ▶` `LeaderboardView`, pulling live from `bot.db.get_leaderboard`/`get_ttt_leaderboard`/`get_number_guessing_scores`. Fonts are the shared `assets/fonts/DejaVuSans{,-Bold}.ttf` (same reasoning as `rank_card.py`/`tictactoe/render.py` — a merged-in draft of this file originally used bare OS font filenames like `"Poppins-Bold.ttf"` that don't exist in the repo and would have silently fallen back to PIL's default bitmap font). PIL rendering runs via `asyncio.to_thread` (a first version of this file and of `tictactoe/cog.py` called their PIL renderers directly on the event loop — CPU-bound and blocking the whole bot for the render duration; fixed to match `rank_card.py`/`onboarding.py`'s existing convention). **Self-updating** exactly like `birthday.py`'s `/kalender`: `(channel_id, message_id, page)` tracked in the `leaderboard_messages` table (one live message per channel, retargeted on repeat `/leaderboard` use), re-rendered in place — at whatever page was last shown — by a `tasks.loop(minutes=REFRESH_INTERVAL_MINUTES)` (10 min) rather than on every XP-granting event. Stale tracked messages (deleted channel/message) are dropped automatically. `LeaderboardView` is **persistent** (`timeout=None`, fixed `custom_id`s, registered once via `bot.add_view(LeaderboardView(self.db))` in `bot.py`'s `setup_hook` like the other persistent views) so the buttons keep working after a restart — same pattern as `ticket_system/views.py`'s `TicketControlView`: the registered instance exists only for click-routing, every actually-sent/edited message gets its own fresh `LeaderboardView(db, page=...)` with the correct page label, and a button click looks up/updates the tracked page in `leaderboard_messages` rather than trusting any in-memory state on the view instance. The level section reuses the same "only show currently-present members" batching logic the old leveling `/leaderboard` had; the Tic-Tac-Toe/Number-Guessing pages show a `Nutzer {id}` fallback for members who've left, matching those features' original (now-removed) leaderboard commands.
- `media_threads.py` — `on_message` listener (not a full command cog) over channel sets built from `config.py` IDs: `MEDIA_CHANNEL_IDS` (`MEDIA_CHANNEL_ID_1`, `SELFIE_CHANNEL_ID_1`) requires an attachment (deletes the message otherwise) and opens a discussion thread on it; `TEXT_ONLY_THREAD_CHANNEL_IDS` (`VORSTELLUNG_CHANNEL_ID_1`, `QOTD_CHANNEL_ID`) skips the attachment requirement but still opens a thread under every message. Deliberately does **not** call `bot.process_commands(message)` — `commands.Bot`'s own default `on_message` already does that, and this cog only adds a `@commands.Cog.listener()` alongside it rather than overriding `on_message` outright, so calling it again would double-dispatch prefix commands.

Every operational Discord snowflake ID (channels, categories, admin/staff roles) is centralized in `config.py` — see the "master config" paragraph above. The only deliberate exception is the large per-option self-assign role catalogs inline in `selfroles.py`/`self_cute_roles.py`.

### Tic-Tac-Toe (`modules/tictactoe/`)

Merged in from a previously separate standalone bot (its own `main.py`/`StandaloneBot`, not carried over — Pixel's own `bot.py` composition root replaces it). Unlike the free-games merge, this one arrived complete — no missing runner logic to reconstruct. Layers:
- `game.py` — pure, dependency-free game logic: `Mark` enum, `Board` (9-cell list, win-line evaluation), `MoveResult`. No Discord/DB imports at all, easy to reason about in isolation.
- `session.py` — `Player`/`GameSession` dataclasses plus `SessionStore`, an **in-memory, per-process** dict of currently-running games keyed by an incrementing `session_id`. Deliberately not persisted (ephemeral runtime state, same category as `number_guessing.py`'s active game) — a restart silently drops any game in progress.
- `stats.py` — just the `PlayerStats` dataclass (`wins`/`losses`/`draws` + `games`/`win_rate` properties) used by `render.py` for the stats card. The persistence layer that used to live here (`StatsStore`, its own `tictactoe_stats.db`) was folded into the master DB's `ttt_stats` table — `cog.py` calls `bot.db.get_ttt_stats`/`record_ttt_result` and wraps the result in a local `PlayerStats` for rendering, keeping `modules/database.py` free of a tictactoe-specific dataclass import (same pattern as `lvl_system/utils/rank_card.py` taking plain values instead of importing `UserStats`).
- `render.py` — builds the game-board and stats PNGs via PIL (`render_game_card`/`render_stats_card`). Fonts were changed during the merge from bare OS-dependent filenames (`"segoeuib.ttf"`, `"arialbd.ttf"`, ...) to the shared `assets/fonts/DejaVuSans{,-Bold}.ttf` absolute paths, matching `rank_card.py`'s approach — the original bare-filename lookup would have silently fallen back to PIL's ugly default bitmap font on any non-Windows host.
- `views.py` — `ChallengeView` (Annehmen/Ablehnen on the initial challenge), `GameView` (3×3 grid of `CellButton`s + Rematch/Statistiken buttons once the game is over), `StatsBackView`. None of these are persistent (`timeout` is finite, no `custom_id`s) — they don't need `bot.add_view` registration, unlike the ticket system's views.
- `cog.py` — `TicTacToeCog`: the `/tictactoe <gegner>` slash command posts a `ChallengeView`; accepting creates a `GameSession` and renders the first board. Turn handling, win/draw detection, and re-render-on-every-move all live in `on_cell_click`. Owns its own `aiohttp.ClientSession` (opened/closed alongside the cog, mirroring `free_games/cogs/checker.py`) purely for fetching player avatar bytes to composite into the rendered card — falls back to a colored initial-letter avatar if the fetch fails.

No `config.py` entries needed — the whole module is guild-agnostic (works in any channel the command is used in) and has no fixed channel/role dependencies.

## Known weaknesses / tech debt (read before adding more features)

- **Permissions are conceptually still split**: `config.ADMIN_ROLES` (tuple, prefix commands) vs. `config.ADMIN_ROLE_ID` (single ID, ticket system's `is_admin()`) vs. `ticket_system/permissions.py`'s own staff-role constants vs. `modules/moderation/`'s native-Discord-permission checks (`ban_members`/`kick_members`/`moderate_members`/`move_members`/`mute_members`, no `config.py` role ID involved at all) are four different checks for "is this person staff", not one. The first three at least all *live* in the same file (`config.py`) so auditing/changing them is a single-file diff, but the logic itself is still not unified into one function — changing staff roles still means updating multiple named constants, and moderation permissions specifically are only editable per-server in Discord's own Integrations settings, not in code.
- **No test suite.** Explicitly acceptable at this scale, but the ticket-slot-reservation race-avoidance logic and the leveling XP math are the highest-value places to add coverage first if that ever changes.
- **Single-process "god bot".** Tickets/applications, moderation logging, XP economy, onboarding, selfroles, birthdays, and mini-games all run in one process, now sharing one SQLite connection too. A hung `tasks.loop` or an uncaught exception outside `setup_hook`'s per-extension try/except can take everything down together, including the ticket system. Considered an acceptable trade-off for a single-guild community bot (splitting into multiple bots trades this for multi-token/multi-deploy/cross-process-state complexity) — not a reason to avoid new cogs, but a reason to keep each cog's failure modes contained (don't let one cog's loop crash the process).
- **In-memory-only state resets on restart** in a couple of places by design (this is about ephemeral runtime state, not persistence — deliberately not stored anywhere): `lvl_system/cogs/leveling.py`'s `voice_xp_tracker` (the 1.5h/24h voice-XP cap) and `number_guessing.py`'s active game/timeout task. A bot restart silently clears these — e.g. restarting resets everyone's voice-XP cap window.
- **`data/tickets.json` was git-tracked** before the SQLite migration (leftover from before `/data/` was gitignored). After the bot's first run under the new code it becomes `data/tickets.json.migrated` on disk; git will show the original as deleted. Worth a deliberate `git rm --cached data/tickets.json` in a follow-up commit rather than leaving it dangling.
- **`modules/modbot/data/cases.json`** is a leftover from the standalone modbot merge (see "Moderation system" above) — real case data for a different (test) guild, deliberately left on disk rather than deleted or migrated. Originally sat at repo-root `modbot/data/`, since moved under `modules/modbot/data/`; either way it's just inert leftover data, not an active module — nothing imports from `modules.modbot`, so it doesn't behave like a real package despite the location. `modules/modbot/data/` is gitignored so it won't get committed, but the file, and the now-empty `modules/modbot/` folder around it, could be removed entirely once confirmed not needed.
- **`data/legacy_free_games.sqlite3` was deleted during the free-games merge instead of being left for `Database._migrate_free_games_db()` to consume.** Its two `posted_deals` rows and the `last_check` timestamp are gone (not git-tracked, no backup); the migration code path itself is still intact and will run correctly if a copy of the old `freestuff.db` is ever dropped back at that path. Practical impact is small and self-healing: at most one duplicate post per deal that was still active when the bot's first real check ran after the merge, after which `free_games_posted_deals` dedups normally.
